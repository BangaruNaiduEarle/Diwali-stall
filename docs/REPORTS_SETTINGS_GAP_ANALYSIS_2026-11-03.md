## 2. Reports

### Existing pages, APIs and reusable components

The request list supports `page`, `limit`, `status`, `q`, `finalizationStatus` (also snake-case alias) and `assignedToMe` (also alias), parsed by [adminCustomerRequestValidation](../server/src/lib/adminCustomerRequestValidation.js). UI search targets customer name/phone; the assignment filter is privileged in the UI. Payment history supports `afterSequence` and `limit`; workflow history supports `afterRevision` and `limit`. These cursors apply to one request. They do not implement date-range analytics, method-level collection totals or complete export traversal.

Reusable visual pieces are request cards, workflow/list audit displays, payment summaries, money/status formatting and the existing stall/season selector. A report must aggregate server-side over the entire authorized result set, not add the current 25-row request page or issue one detail/payment request per bill. Quotation WhatsApp/order-confirmation payloads are transactional messages, not report exports. Files called audit/mapping reports under scripts/server reports are developer tooling, not operational Reports UI/API.

Every standalone type below is **not implemented**, even where its underlying transactions exist. The proposed minimum covers requests, finalized billing and receipts/balances; business approval must settle whether product/profit/activity/export extensions are required for release.

### Missing filters and precise query contract

Proposed report parameters: `from`, `toExclusive`, `dateBasis`, grouping/sort, stable cursor/limit; applicable request/finalization/payment status, source, creator, assigned recipient, finalizer, payment actor/device, method, recording mode, customer search, product/category/pack variant and unit. Each report must reject unsupported combinations rather than silently ignore them. Existing list `status/q/finalizationStatus/assignedToMe` is partial reuse, not evidence that these aggregate filters exist.

Stall and operating season are **validated session context**, using existing `X-Admin-Location-Id` / `X-Admin-Season-Id` selection. They are not unrestricted client `businessId` filters. Derive business from the authorized location. A historical season requires its own membership; all-season/all-stall totals are not part of the proposed initial contract. Product/category joins must follow location ownership: permanent-location catalogues intentionally span operating seasons, while requests, bills and payments also require the selected season.

Use a documented timezone (proposed `Asia/Kolkata`) to translate local calendar boundaries to UTC with half-open ranges. Distinguish request creation time, finalization event time and payment `occurred_at` versus server `received_at`. An offline receipt can arrive later than its occurrence; one date basis must not silently substitute for the other. `updated_at` changes after payments/edits and is not an authoritative sale date. Historical unknown actors/times stay unknown; finalization time can be derived from the relevant workflow event only when present.

### Calculations and data sources

| Metric | Required rule / existing source |
| --- | --- |
| Quoted subtotal / discount / quotation total | Sum saved `quotation_items.line_total_paise` once per selected quotation; stored subtotal and adjustment must reconcile to stored total. Selling snapshots/overrides are historical evidence; do not reprice with today's product selling rate. See [savedBillPricing](../server/src/lib/savedBillPricing.js) and [bill-adjust policy](../server/src/lib/billAdjustmentPolicy.js). |
| Final bill due | For an eligible finalized account, `request_payment_accounts.amount_due_paise` is the frozen accepted-amount basis. Do not substitute quotation total or count a draft as revenue. Distinguish finalized sales value from collected cash. Existing accounts require a positive valid accepted amount; closed historical records without one need an explicit unavailable-basis bucket, not fabricated receivables. |
| Received / outstanding | Sum only ledger `entry_type = PAYMENT`; outstanding = frozen due minus received. Use scoped `request_payment_summaries` for current state. HOLD does not add payment or cancel outstanding. Payment-status precedence in the existing view is no-account UNPAID, fully paid PAID, then HOLD, then PARTIAL/UNPAID; retain separate eligibility so no-account rows are not misreported as payable debts. |
| Period collections | Sum payments whose chosen payment timestamp falls in the range, regardless of original bill's creation date. Group ONLINE/OFFLINE separately from CASH/UPI/CARD/BANK/OTHER. Later payments on already closed bills count in their own receipt period. |
| Historical as-of balance / HOLD | Existing views are current, not as-of. Recompute payment totals and most recent HOLD/RELEASE_HOLD through the cutoff, and include only accounts finalized by that cutoff with known evidence. Never filter today's balance by an old date and label it historical. Specify unavailable legacy dates. |
| Product quantities/value | Use saved unit type and stable request-line/quotation-line identity; group boxes/pieces/whole fixed packs separately. A pack sale and its descriptive components are different measures. Agreed-bill amount/discount allocation is a new rule if product-level realized revenue is requested; avoid multiplying the entire bill amount across lines. |
| Current cost / estimated profit | Existing helper reads `product_purchase_rates` where `effective_to IS NULL`, floors per-piece cost from pack cost/pieces-per-pack, and returns quotation total minus estimated cost only when all supported lines have known valid costs. This is a current estimate, not profit against the frozen accepted amount; preserve the label or introduce a separately named approved calculation. No automatic Family Pack cost inference. |
| Historical profit / margin | Define approved cost-at-sale valuation, loose-unit rounding, pack cost source, discount/agreed-amount allocation, missing-cost coverage and revenue basis. With complete frozen costs: proposed gross profit = final due minus recognized cost; margin = profit / final due, with explicit zero/unknown handling. Never average line percentages to get overall margin. Current rates and `private_rates` X4/final references are not historical cost. Partial aggregates must disclose unknown coverage, not imply complete profit. |
| Final Price + ₹500 | Reference-only (`bargainingReference` adds 50,000 paise). Never contributes to due, receipts, outstanding, revenue or cost/profit calculations. Do not introduce a setting that changes this billing invariant. |
| Arithmetic / totals | Integer paise throughout, safe-integer overflow checks including aggregate sums; round only under the explicitly adopted unit/allocation rule. Paginated row totals must reconcile to full-set summaries; joining multiple ledger/events/quotation versions must not multiply bill amounts. |

Refunds, expenses, tax accounting and physical stock-movement valuation are not supported by the inspected payment ledger/stock-status model. A report must not invent these data sources. Requiring them would expand the implementation beyond this proposed release slice.

### Permissions and isolation

Current [role helpers](../server/src/lib/adminRoles.js) allow Owner/Super Admin sensitive pricing, finalization and payment recording; Admin can read scoped operational requests/payment summaries/history but cannot record payments/HOLD or change privileged financial values. Workflow presentation recursively strips cost/profit/margin fields and limits Admin price/amount history. This is existing behavior, not a new Reports permission policy.

Proposed Reports policy: Owner/Super Admin read scoped operational/financial reports and exports; Admin receives only explicitly approved operational/request/selling/payment-status views, never purchase/cost/profit/margin or privileged adjustment metadata. Whether Admin may see full stall collection totals, references or other actors' summaries must be explicitly approved; existing per-request read access does not automatically grant new aggregate access. Default-deny unapproved financial report types for Admin. Role changes and exports must be enforced server-side with allowlisted response projections, not UI hiding. Platform Admin without operational membership has no stall Reports access.

Use the **lesser of season and location roles**, not `admin_users.role` alone. An Owner in A who is Admin in B remains Admin in B. Guard every aggregate, row, drill-down, export and reference query by authorized business/location/season; membership removal must immediately block new reads. Historical reads may be allowed with explicit membership, while writes remain denied. `Cache-Control: no-store` and existing stale-context rejection must apply; do not place financial Reports in shared service-worker caches.

### Required Reports changes

1. Add operational report dispatcher/service(s), filter validation, scoped parameterized SQL, aggregate/detail response schemas and field-level role projections. Proposed routes: `GET /api/admin/reports/summary`, `/requests`, `/bills`, `/payments`, `/outstanding`; optional `/sales-lines`, `/activity`, `/profit` and export representation only after scope approval. These are proposed new routes, not existing APIs. Scope summary/rows together and return normalized filters/date basis, scope, generation timestamp and metric basis/coverage.
2. Add `/admin/reports`, report sections, applicable filters, aggregate cards, paginated rows and authorized existing request drill-down. Add navigation and destination/route-role allowlists in [adminWorkspaceAccess](../src/admin/lib/adminWorkspaceAccess.js) / [adminNavigation](../src/admin/lib/adminNavigation.js). Existing API [client](../src/admin/api/client.js) and [adminSeasonRequest](../src/admin/api/adminSeasonRequest.js) already scope operational paths generically; use them rather than inventing a parallel selection mechanism.
3. Cancel/ignore stale report responses when context changes; clear filters containing foreign actor/product IDs, totals and export state on stall/season switch. Reports are online authoritative by default; an offline page must say unavailable/stale and never count pending outbox operations as server-finalized sales. Offline report persistence is not necessary to implement standalone online Reports.
4. Use existing transaction tables/views for operational/bill/payment reports. New financial mutations or report-total tables are unnecessary. Profile scoped queries later on disposable representative data before adding only justified indexes. Historical cost snapshots are a separate conditional schema requirement below.

### Proposed minimum independent settings contract

**Partially implemented:** stall identity and scopes exist. **Not implemented:** durable independent contact/presentation/schedule editing, settings read/write API/UI, revisions, audit and consumer resolution.

Proposed v1 fields:

- Stall profile: authorized display/stall label and venue/address using existing location metadata; WhatsApp/phone, map URL and optional location detail lines as new profile fields. Business-level branding inheritance versus stall override requires one explicit rule.
- Season settings: operating date list/range and display timings, optionally season-specific contact/venue override only if required. Start with explicit typed fields; no unbounded arbitrary JSON keys that can become financial/security settings.
- Response metadata: validated business/location/season, effective read/write capability, revision(s), update time and actor; identify fallback/default versus saved values. Separate a public projection from the management representation.

Proposed authorization: Owner **and Super Admin** may read/update the selected stall's approved settings in a writable active context. Admin gets only necessary public/operational display projection, no settings management mutation; management read can be denied entirely to keep its contract simple. Platform status alone grants no operational edit. Require valid season and location memberships and revalidate them with the conditional write, including disabled/archived context; do not let a role captured before an awaited operation authorize a later commit.

Profile fields belong to a location across seasons; schedule belongs to the operating season. Editing a shared profile must explicitly be an active-context operation and must not pretend to update only an archived season's historical identity. If immutable historical bill branding/contact is a release requirement, capture an issuer-settings version/snapshot for new finalizations; current mutable profile data cannot reconstruct the past. This extra requirement is not established by the earlier reports and should not be silently bundled into settings CRUD.

### Required Settings API/UI/consumer changes

Proposed routes: `GET /api/admin/settings` for an authorized scoped management response and `PATCH /api/admin/settings` for allowlisted profile/season changes with expected revisions. The route name matches the missing Scenario 5 probe; it is a proposal, not an implemented contract. Return 400 for unsupported/invalid fields, 403 for insufficient/archived authority, 404 for foreign records, 428 for a required missing revision and 409 for stale revisions. Never let body scope/actor values override the authenticated context.

Save changed fields, revision increments and a dedicated settings audit event in one atomic batch. Repeated unchanged saves must not create unrelated business operations; if an operation ID/idempotency receipt is adopted, same-ID retries replay the same result and altered payloads conflict. Financial workflow receipts/events must not be repurposed for settings without a separately designed contract. Independent stalls must not contend on a global revision.

Add `/admin/settings` page, navigation, Owner/Super Admin route capability and API adapter, validation/error/conflict handling, selected-stall header and archived read-only display. Guard direct URLs as well as links. Super Admin must not be routed through the currently Owner-only `/admin/business` gate to reach settings. Clear unsaved edits and discard late responses on context switches; a form opened in A must never save into B.

Introduce one scope-aware settings resolver used by consumer code. Admin consumers resolve the selected authorized context; public consumers use the existing trusted public tuple. Add a safe public settings projection endpoint or include presentation settings in the public catalogue response, with public caching keyed by trusted tuple/settings revision. Public fields only; never reuse the full management response. Update [siteConfig consumers](../src/data/siteConfig.js), especially header/footer/venue/announcement, WhatsApp helpers/floating button and customer pickup-date helpers. Preserve the current global public site when no multi-stall public selector exists; do not show Admin B's contact on the public A catalogue.

For offline billing, cache only needed presentation settings with existing business/location/season preparation plus version and capture time; do not fetch another stall's fallback. Settings updates can remain online-only in v1. Existing offline QR, Family Pack snapshots, operation IDs and bill arithmetic must remain unchanged. A later contact/schedule edit must not mutate already queued requests or signed cart contents. If offline setting edits are later required, they need a new explicitly authorized sync/conflict design.

## 4. Database and migration impact

**A new additive schema migration is required for durable independent settings under the proposed contract. None is created or applied here.** Merely exposing the existing global singleton cannot satisfy independent settings. Reusing existing name/address fields alone would still omit contacts/schedules, conflict detection and atomic settings history.

| Change | Necessity / proposed structure |
| --- | --- |
| Location settings persistence | Required: new `location_settings` keyed by `location_id` with FK to `business_locations`, typed contact/map/detail/display-override fields where not already canonical, revision and updater metadata. Reuse canonical location name/address/stall label; an atomic settings write can update these plus increment the location settings revision. Derive business through the parent or enforce a composite ownership FK if duplicated. |
| Season settings persistence | Required for dates/timings: new `location_season_settings` keyed by `(location_id, season_id)` with composite FK to `location_seasons`, schedule fields, revision and updater metadata. Add JSON validity plus application validation for typed date/detail arrays if JSON storage is chosen. No global default row shared by all stalls. |
| Settings history | Required for proposed audited saves: dedicated append-only settings events keyed by event/operation ID, scoped target, actor/effective role, occurred/received timestamps, old/new revisions and allowlisted changed fields. Profile events identify location-wide target plus authorization season; season events bind the exact season. Atomic failure rolls back settings and history together. Do not use request history: its rows require a request and request revision. |
| Report persistence | Not required for the proposed online request/bill/collection/current-balance reports. Reuse 0021 workflow history and 0022 accounts/ledger/views; read with new scoped queries. Optional scoped date/filter indexes only after query-plan evidence. No financial total backfill or materialized aggregate is justified by inspection alone. |
| Historical cost snapshots | Conditional: required only if frozen historical profit is a release report requirement. Introduce immutable per-finalization/line cost basis with unit/pack version, exact rounding, source and unknown marker; integrate atomically with existing finalization. Preserve old costs as unknown rather than reconstructing from today's rates. Current rate effective dates do not prove old finalization valuation or complete pack costs. |
| Issuer settings snapshots | Conditional: if unchanged historical bill/receipt presentation is required, save issuer profile/settings version for new records; show legacy absence explicitly. Not required just to create an online settings editor. |

Use the next available migration after the existing chain; do not edit or rerun 0018/0020–0024. Update the schema/test fixture definitions used by future focused tests, not original databases. New schema availability should have a clear fail-closed response rather than a silent cross-stall static fallback. Rehearsal, rollout, backup and recovery approval remain separate future tasks.

### Existing single-stall compatibility

The checked-in 0020 foundation maps the existing 2026 records to `business-diwali` / `location-diwali-2026` / `season-2026`. These are source-defined identities, not values newly verified from a database here. A future migration/seed must validate the mapping rather than assume it for arbitrary installations.

Preserve current static contact/location/schedule behavior for that verified original stall: seed new settings from the existing source defaults or provide an explicitly restricted, versioned legacy-default resolution until its settings are saved. Do not overwrite existing non-null canonical names/addresses, clone private contacts into every newly provisioned stall, assign legacy historical/unmapped rows to a new stall, or change historical transactions. New stalls must have their own initialized settings or clearly empty fields.

Explicit legacy mode (`ADMIN_LOCATION_MODE=false`) is distinct from a single location in location mode. Existing payment service requires a validated location, so legacy mode cannot simply call new payment-report/settings APIs with a fabricated location. Preserve legacy behavior and either define an explicit supported legacy mapping adapter validated against the original stall, or leave new scoped features unavailable with an actionable prerequisite until location mode/schema is authorized. Missing/invalid mode or context must fail closed. Do not auto-enable a runtime flag or apply a migration to make the feature appear available.

Keep the Platform singleton and trusted public tuple behavior unchanged. Verify the existing one-stall public catalogue/request flow, WhatsApp links and pickup dates render the same effective defaults. A settings edit should affect only its intended stall/season and appropriate future consumers, not historical prices, final bill/payment balances or pending outbox identities.

## 6. Implementation boundary and release disposition

The smallest viable scope is standalone online request/bill/collections/outstanding reports using current transactional sources, plus Owner/Super Admin-managed independent stall contact/presentation and season schedules with atomic revisioned saves. Product breakdown, historical profit, as-of reporting, exports, historical issuer snapshots and public multi-stall selection must each receive an explicit scope decision; none should be disguised as already supported.

Before implementation, confirm the report catalogue/filters, Admin aggregate visibility, editable field list, shared-profile versus season rules, and profit/time/default semantics. Then authorize the additive settings schema and bounded API/UI work separately. **Release remains NO-GO:** required Reports and Stall Settings remain absent, and this source inspection does not close their NOT TESTED acceptance rows or the Android/runtime gates.
